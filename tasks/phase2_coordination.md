## Roles (strict separation — no role does another's job)

| Role | Mandate | Explicitly NOT this role's job |
|------|---------|---------------------------------|
| **Planner** | Investigate the codebase, produce a concrete, file-level task breakdown with acceptance criteria, resolve open judgment calls, flag risk/sequencing | Writing/editing any code, tests, or docs |
| **Builder** | Implement the planner's spec (source + config + prose docs) | Writing new tests, running the full validation suite, signing off on its own work |
| **Tester** | Write the regression/smoke tests the plan calls for, run the full suite, report pass/fail in detail | Fixing implementation bugs it finds, implementing new features |
| **Validator** | Independent re-verification (suite, lint, types, scope check, review), explicit PASS/FAIL verdict with itemized findings | Fixing anything itself — kicks issues back to Builder/Tester |

| 2 | P2-2: are all 7 `(str, Enum)` domain enums safe to migrate to `StrEnum`? | Yes — GO for all 7 (`ExecutionModel`, `OrderSide`, `IndicatorType`, `Comparison`, `PositionSizeType`, `StopLossType`, `TakeProfitType`). None overrides `__str__`; every serialization path is `.value`-based (Pydantic `model_dump_json` + explicit `.value` call sites in `strategy.py`), so output incl. `strategy_hash` is byte-identical. Tester must add a serialization-stability test (hash + round-trip unchanged pre/post) — static analysis clears the design but the test is the actual proof. Partial migration must keep the `UP042` ignore; only drop it once all 7 are done. |
| 3 | P2-3: bump the pre-commit ruff pin up to match `.venv`, or downgrade `.venv` to match the old pin? | Bump up to `v0.15.16` (confirmed installed version) — matches what `make format` already runs; downgrading would fight `pyproject.toml`'s floor on every reinstall. Confirmed no `[tool.ruff]` config breakage across that version span. One-time reformat of 5 files (assert/call wrapping only) is expected, cosmetic, and is this item's actual diff. |
| 4 | P2-4: require `broker_order_id` + reject `record-fill` in paper mode, or the reverse? | Confirmed by tracing callers: `record-fill` is exclusively the live-mode bookkeeping path — paper fills are produced by `live run`'s own auto-fill, never by `record-fill` (its docstring already says "live mode"). Reject `record-fill` when `universe.mode == "paper"`; require `--broker-order-id` unconditionally (it's a live-only command). Both new fields (`PaperFill.broker_order_id`, `TradeIntent.broker_order_id`) default to `None` — additive, zero migration of existing `livetrade/*_ledger.json`. |
| 5 | P2-5: confirmation flag vs. call-stack/invocation inspection? Should `resume()` also re-verify halted state? | Keyword-only `confirm: bool = False` raising `ValueError` when falsy — stack inspection rejected as brittle/untestable for a one-caller method. No added "must currently be halted" guard inside `resume()` itself: the CLI already checks that and prints its own message before calling `resume()`; a no-op resume on a non-halted ledger is harmless today and adding the check would change the method's contract beyond this item's scope. |
| 6 | P2-6: does the Robinhood MCP expose account identity, and should the check become code? | Yes (`get_accounts` → `agentic_allowed`/nickname/masked number) — but the check stays runbook-only by necessity: `src/bonito/` never contacts Robinhood (the MCP boundary lives entirely inside the Claude session/Routine), so enforcing it in Python is architecturally impossible without inverting that boundary. | 7 | P2-7(a): is `IntelligentChart.tsx` V1 really a zero-importer dead file? | Premise is technically false (`AnalysisView.tsx` renders JSX literally named `IntelligentChart`) but resolves true after alias-tracing: that local name is bound to **V2** via `dynamic(() => import("./IntelligentChartV2"))`, so V1 is reachable only through an unused `index.ts` barrel re-export (nothing imports the barrel). V1 is the sole importer of the `indicators/registry/`+`indicators/base/` subsystem, which becomes orphaned by this deletion — deferred to Phase 3 (pairs with its existing "archive orphaned files" item), deliberately NOT pulled into P2-7's scope. |
